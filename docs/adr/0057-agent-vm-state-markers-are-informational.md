# Agent VM 状态标记不再是准入条件

## 状态

已接受（取代 `SPEC.md` 原先「不声明数据库中每个标记就不得激活」的规定，以及 ADR 0056 中同名要求）。

## 背景

蓝绿发布让两个不同版本的二进制共用同一份 rqlite 业务库。为了让旧代码不误处理新数据，系统引入了带版本的状态能力标记（`state_capabilities`）与发布清单的 `state_compatibility`，并在三处强制执行：

1. 槽位启动时比较清单声明与数据库标记；
2. Deployd 在回滚前校验目标槽位的标记；
3. Deployd 在激活、恢复与好转时要求两个槽位的标记集合一致。

2026-11-23 的 1.10.0 部署暴露了这套准入的代价。候选槽在 `stage` 阶段被启动一次，就把 `vm-hold@1` 写入了共享数据库；随后 stage 失败，补偿路径重启旧槽时旧 release（1.9.3）因不认识的标记而拒绝启动，回滚也随之失败，事务进入 `needs_recovery`，两个槽位都没有在跑，而当时已发布的恢复动作（`rollback`、`finalize`）都依赖旧版本可启动。

引入标记的初衷是防止旧版本静默破坏新语义（例如把 pinned 的 VM 当作过期资源销毁）。但由此得出的「任何标记差异都禁止启动」把运维者排除在决策之外，并把一次未完成的 stage 变成了不可自愈的宕机。

## 决定

1. **部署面不过问被部署服务的能力。** Deployd 与 CLI 不解析、不比较、不据此拒绝任何动作；`state_capabilities` 仍随观测透传，用于状态展示与排障。
2. **服务自己也只记录不阻断。** 槽位启动时若数据库包含清单未声明的标记，记录告警与状态字段后照常运行。
3. **降级后果由运维者承担。** 不引入任何显式同意开关、能力分类或回滚窗口限制；`rollback` 可以被重复执行，`complete-forward` 只在旧版本确实起不来时由运维者选择。
4. **数据库降级仍被禁止。** 标记只描述事实，不得据此改写、回填或迁移既有数据。
5. **清单声明改为格式校验。** 发布清单可以只声明自己认识的部分标记，不再要求与构建时的完整列表逐项一致。

## 后果

- 旧版本可以对着更新的数据库启动，因此它可能按旧语义处理新形态的数据（ADR 0056 的 pinned VM 场景）。这是被明确接受的风险，运维者必须在降级前自行判断。
- 恢复路径不再被能力差异卡住：`retry-stage`、`rollback`、`complete-forward` 只依赖身份、就绪、静止与角色证据。
- 状态标记的正确定位是**观测与审计**：`drain-status`、`status`、部署证据继续记录标记差异，但没有任何路径用它来拒绝动作。
- 需要真正阻止旧代码运行的场景（数据格式不兼容）必须在服务内部以读写失败暴露，而不是由部署面预判。
