# Agent VM 恢复点预算按角色而不是年龄释放

## 状态

已接受（取代 ADR 0054 与发布合同中「最旧的第三个恢复点必须满三十天才可删除」的规定）。ADR 0054 的其他决策保持不变。

## 背景

每次蓝绿 `stage` 或显式 `rollback`，部署控制服务都会在改动槽位角色前登记一个已验证的 rqlite 状态恢复点。同一状态权威最多保留三个点，最新两个始终受保护，最旧的第三个原本还要满三十天才允许清理；否则返回 `backup_storage_exhausted`，拒绝本次部署。

这条年龄条件把两种不同的保护混在了一起：**恢复能力**（哪些点还可能被 `retry-stage`、`rollback` 或未完成事务选中）与**材料留存**（多久之后才算过期证据）。它带来的直接后果是部署节奏上限：

- 2026-11-23 一次 stage 占一个点；
- 2026-11-24 的 1.10.3、1.11.0、1.12.0 三次升级各占一个点；
- 三个点全部未满三十天，`stage` 在第一步就被拒；
- 只有手工把最旧的点移出预算目录，升级才能继续。

稳态下，删一个点要等三十天，于是「每天升级」被改写成「每三十天升级一次」。而第三个点在成为可删候选时，已经比另外两个都旧，且不在回退目标、租约或未完成事务的引用范围内——它不具备任何恢复角色。

## 决定

1. **预算释放只看角色。** 最旧的点只要不在最新两个之内、没有有效租约、不是任何未 finalized 事务或其 stage 恢复点、不是当前回退目标，即可删除，年龄不参与判定。
2. **容量门禁不变。** 全部恢复材料仍受 1 GiB 实际字节上限约束；容量不足时继续返回 `backup_storage_exhausted`。
3. **删除仍留证据。** 删除前先持久化 `pruned-<id>.json` 收据，中断后只完成已批准的删除。
4. **新增受支持入口。** `agent-vm-deploy recovery-points` 展示每个点的 `blockers`，`prune-recovery-points` 按同一判定逐个回收可清理的最旧点。运维者不再需要手工移动目录。
5. **不再保留按龄清理。** 恢复点不存在后台过期清理路径；年龄从合同的恢复点规则中移除，避免出现「文档说三十天、代码从不执行」的空洞承诺。

## 后果

- 部署节奏不再受恢复点数量限制：三次以上连续部署会自动回收最旧的点。
- 可删除的最旧点可能很新（分钟级），但它在删除时刻已经不承担任何恢复职责；回退能力仍由最新两个点与回退目标保证。
- 审计仍能通过删除收据、事务记录和阶段事件还原「哪个点、何时、因何被删」。
- 若未来需要保留更长的取证窗口，应以独立的外部备份或显式的归档动作实现，而不是把留存期重新塞回预算门禁。
