# CI 用时优化需求与设计

## 状态

本文是 CI 优化的需求与设计收敛记录，当前只定义调查、目标、方案和实施顺序，不修改 workflow，不改变质量合同，也不代表方案已经实施。

## 已确认的问题

最近五次成功的 CI (PR) 端到端耗时为 12分22秒、11分50秒、15分25秒、16分45秒和 22分53秒，中位数为 15分25秒。样本较小，后续实施前需要扩大到至少 20 次成功 PR run，并分别记录排队时间、Ubuntu 执行时间、macOS 执行时间、关键路径和 runner 分钟。

Run 42084608528 显示 Ubuntu 从 18:28:48 到 18:36:42 执行约 7分54秒，macOS 从 18:36:44 到 18:41:06 执行约 4分22秒；macOS 在 18:28:45 创建后约 8 分钟才开始。jobs.startedAt 是执行开始，不等于排队结束前的端到端耗时。

当前 PR 和 Main 都使用同一个两项 OS matrix，且 `max-parallel: 1`，导致同一 run 内 Ubuntu 与 macOS 串行。Ubuntu 关键串行段中，Skill tests 约 2分05–2分20秒，Linux race tests 约 1分05–1分07秒，隔离 rqlite 集成约 49–63秒；其余检查还包含重复的依赖安装、typecheck、Go tests、vet、repository tests 和 policy-like checks。

当前没有证据证明 macOS 是必需门禁。workflow 在 macOS 上执行的是与 Ubuntu 基本相同的通用 Bun、Web、Go 和静态检查，仓库尚未发现明确的 macOS 专属测试、原生系统 API 合同或平台发布产物。因此 macOS 的保留理由必须先通过代码、历史失败日志或真实平台行为验证；不能把“现在有 macOS matrix”当作必要性证据。

## 需求与目标

第一阶段的优化目标是把代表性 PR 的实际执行时间压到 6 分钟以内，同时保留现有质量检查和失败条件。端到端等待时间作为观测指标，不在本阶段承诺固定上限，因为排队受 GitHub-hosted runner 供给影响。

第一阶段不引入付费 runner、自托管 runner、远端设置变更或质量覆盖下降。任何路径分层都必须有显式映射、审计记录和 Main 行为说明，不能通过静默跳过检查制造速度收益。

需要持续记录四类指标：从 run 创建到完成的端到端时间、每个 job 的排队时间与执行时间、关键步骤的墙钟时间、按 job/OS 计算的 runner 分钟。失败 run 与成功 run 分开统计，600 秒观察窗口不作为 CI timeout 或性能证据。

## 设计原则

1. 先消除等待和重复，再讨论平台边界；不以删除覆盖或放宽成功条件提速。
2. 每个检查必须有唯一归属：快速 PR 门禁、条件性深检查或 Main 全量检查；避免同一检查在同一 job 中重复串行执行。
3. 平台触发条件必须由实际依赖证明。macOS 仅在确认存在 macOS/原生边界且变更命中该边界时运行；在证明之前，macOS 不能被描述为必要检查。
4. PR 同一分支允许取消过时运行，Main 保持不取消，以减少过时提交消耗并保留主分支完整验证。
5. 所有优化先以试运行和指标对比验证，再固化为质量门禁合同。

## 方案比较

| 方案 | 预期收益 | 正确性风险 | 复杂度与成本 | 结论 |
| --- | --- | --- | --- | --- |
| 把矩阵并行化并拆成职责清晰的 jobs | 直接消除约 4–8 分钟的 macOS 等待，并缩短 Ubuntu 串行关键路径 | 需要处理共享依赖、artifact 和 required checks | 低到中；使用现有 GitHub-hosted runner | 首选基础措施 |
| Bun/Go 依赖缓存与安装复用 | 减少每个 job 的安装和工具初始化 | 缓存失效或错误命中会造成隐蔽问题 | 低；需验证 cache key 和冷缓存表现 | 与并行化一起实施 |
| PR 路径分层，Main 保持全量 | 对文档、纯 Go、纯 Web 等变更减少无关等待 | 路径映射错误可能漏跑检查 | 中；需要映射表、审计和回退规则 | 按已收敛决定实施，但不得无记录跳过 |
| macOS 仅相关变更运行 | 可能消除无必要的 macOS runner 分钟与排队 | 若平台依赖未被识别会漏检 | 中；先做依赖盘点与历史失败回放 | 先验证必要性，再实施 |
| PR `cancel-in-progress` | 减少过时提交占用和排队 | 取消中的 run 不可作为完成证据 | 低；Main 保持非抢占 | 采用 |
| 付费或自托管 runner | 可能降低排队 | 成本、维护和隔离边界增加 | 高；超出第一阶段 | 暂不采用 |

## 推荐目标形态

把 CI 分为并行的职责 jobs：静态/类型与 Web 单测、Go 单测与 vet、Linux 专属集成与 race、构建与 artifact、条件性平台检查。每个 job 只安装自己需要的运行时，并通过稳定 cache key 复用 Bun 与 Go 下载缓存。required checks 应绑定到聚合 gate，由 gate 汇总已运行的检查结果；条件性检查必须在 workflow summary 中显示触发原因和未触发原因。

PR 路径分层采用显式 allowlist：文档或只改 CI 文档的变更走快速门禁；Web 变更触发 Web、E2E、Storybook 和静态构建；Go 控制面变更触发 Go、rqlite、vet 和 race；workflow、release、agent-vm-ops 或跨层变更触发全量门禁。分层规则需要覆盖未知路径，未知路径回退到全量。

macOS 触发前必须完成平台依赖盘点：搜索脚本、原生模块、系统调用、路径/权限差异、历史 macOS-only 失败和发布合同；对每项依赖写出可复现的最小测试。若盘点不能证明必要性，应把 macOS 从 PR 必需检查中移除或改为定期兼容性任务；若证明必要性，则只对命中平台边界的变更运行，并保留 Main 的周期性全量平台验证。

## 实施步骤

1. 扩大 20–30 次成功 PR 和 10–15 次成功 Main 样本，导出 job/step 时间、排队、结论和 runner 分钟。
2. 建立检查目录，给每个现有 step 标注合同、耗时、平台依赖、是否重复、建议 job 和变更路径。
3. 完成 macOS 必要性调查，补充最小平台证据或决定将其降级为条件/周期任务。
4. 在不删检查的前提下拆分并行 jobs，加入 Bun/Go 缓存，并保留聚合 required gate。
5. 启用 PR 过时运行取消，保持 Main 非抢占；观察失败率、取消率和排队变化。
6. 以 feature branch 试运行至少 20 次，比较 P50/P90 执行时间、端到端时间、runner 分钟和失败分类；只有指标达标后才进入正式 workflow 变更审查。

## 验证与回滚

成功标准是：代表性 PR 实际执行时间 P50 ≤6 分钟；所有现有质量检查仍有明确归属；未知路径回退全量；失败率与基线相比没有统计上显著恶化；Main 全量检查继续通过。若缓存命中率低、路径误判、平台漏检或失败率上升，立即回退到上一版 workflow，保留指标和失败样本重新设计。

## 未决事项

macOS 的真实必要性、路径分层的最终 allowlist、required check 聚合方式、缓存命中率目标和 GitHub runner 配额仍需在实施前由证据确认。付费 runner、自托管 runner、远端仓库设置或质量合同变化属于后续单独决策，不在本文授权范围内。
