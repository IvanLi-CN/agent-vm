# Agent VM 文档来源与 Web 审阅研究

## 问题与结论

项目计划建设独立维护的文档子项目，为用户提供使用说明，为开发者解释系统设计，并在设计阶段提供 Web 审阅。Fumadocs 选型已经确认，理由见[技术方案](agent-vm-documentation-stack.md)，当前需求和验收见[文档审阅 Spec](../specs/documentation-review/SPEC.md)。未来可能以 MPA 或 SPA 方式与管理界面集成；具体集成方式和托管服务尚未确定，本研究不构成实施或公开发布授权。

建议将问题定义为“同一份内容如何生成不同阅读入口”，而不是“如何让 Markdown 和 MDX 两份正文同步”。设计正文继续保存在既有 Markdown 路径，站点优先直接读取；存在路由、元数据或资源适配需求时，在构建期增加小范围适配。MDX 只用于确有交互需求的站点页面，不作为全部设计文档的必选格式。

独立子项目意味着构建配置、主题、组件、导航及产物边界独立，不意味着复制正文或立即拆成另一个仓库。同仓库的独立子目录更容易让正文、站点代码及适配规则在同一提交中接受审阅。

完整站与生产／Demo 内上下文帮助的具体推荐技术方案、共享模块和目录布局见[文档技术方案与工程组织](agent-vm-documentation-stack.md)。富交互页面允许以 MDX 为唯一来源，长期合同继续保留 Markdown；单源原则不要求所有设计材料使用同一种扩展名。

## 仓库证据

- [文档导航](../README.md)已经区分产品、架构、长期合同、ADR、运维和研究建议，并要求区分目标设计与实现事实。
- [主题索引](../specs/README.md)将长期需求、实现覆盖与启用事实分别交给 `SPEC.md`、`IMPLEMENTATION.md` 等材料。站点应保留这些职责，不能把需求被接受或合并等同于功能已上线。
- [产品定义](../../PRODUCT.md)使用 HTML 注释；[系统架构](../architecture/system.md)包含 Mermaid；ADR 使用既有 frontmatter；合同包含表格和显式 HTML 锚点，例如[部署观测锚点](../specs/agent-vm/contracts/observability.md#deployment-control-observation)。这些都是实际适配样本。
- [Spec 检查器](../../bin/spec_contract_check.ts)限定规范来源为 `docs/specs/<slug>/SPEC.md`，并检查 `REQ-*`、`VER-*`、固定章节和 `../../adr/*.md` 链接形式。迁移扩展名或改写源文件路径会影响既有合同。
- [文档测试](../../bin/test_agent_vm_documentation.py)验证既有合同结构与部分内容、链接，不是站点路由、完整锚点或跨文档语义的一致性证明。

因此应让 Web 适配层兼容当前来源，而不是先为框架批量迁移设计文件。已有文档之间的链接是否全部有效也需要验证，不能将既有问题误判为站点转换造成的问题。

## 已查证的格式与框架事实

| 事实 | 对项目的含义 | 官方来源 |
| --- | --- | --- |
| MDX 支持 Markdown、JSX、表达式及模块导入，但 HTML、HTML 注释、自动链接、缩进代码以及部分裸字符的规则与普通 Markdown 不同。 | 不能通过修改扩展名就假设兼容；现有 HTML 注释尤其需要处理。 | [MDX 格式说明](https://mdxjs.com/docs/what-is-mdx/) |
| MDX 编译器默认不启用 GFM 和 YAML frontmatter；可以通过插件增加支持。 | 表格、元数据等需要核验具体集成的配置；不能将框架集成后的能力视为 MDX 格式默认能力。 | [GFM](https://mdxjs.com/guides/gfm/)、[Frontmatter](https://mdxjs.com/guides/frontmatter/) |
| MDX 工具链可以按文件扩展名或 `format` 选项区分普通 Markdown 与 MDX。 | 即使选择支持 MDX 的技术栈，也不要求所有 `.md` 按 MDX 语法解析。具体框架仍需验证。 | [MDX 格式说明](https://mdxjs.com/docs/what-is-mdx/) |
| VitePress 支持 Markdown 文件路由，项目根与源目录可以分开配置；`.md` 页面链接受支持。 | 站点工程与内容目录分离是现成能力，但根目录产品文档、源目录外资源和 README 目录映射仍需样本验证。 | [VitePress 路由](https://vitepress.dev/guide/routing) |
| Starlight 支持 `.md`、frontmatter 及标题锚点；每页需要标题元数据，Markdown 与 MDX 的具体语法支持存在区别。 | 可以保留 Markdown，但需解决缺少站点字段的来源如何获得页面元数据。 | [Starlight 内容编写](https://starlight.astro.build/guides/authoring-content/) |
| Astro 内容集合将内容读取与页面生成分开，集合内容需要通过页面路由呈现。 | 外部内容加载能力不等于完整的文档导航、搜索和链接转换；Starlight 的具体接入也需单独验证。 | [Astro 内容集合](https://docs.astro.build/en/guides/content-collections/) |

上述资料证明单一 Markdown 来源具有技术可行性，没有证明已选框架无需改造即可适配本仓库。具体依赖版本和插件组合在实现时验证落锁，最终 MPA／SPA 集成方式在后续接入阶段确认。

## 方案比较

| 方案 | 正文所有权 | 代价与适用边界 | 建议 |
| --- | --- | --- | --- |
| 站点直接读取既有 Markdown | 仅维护源文件 | 转换最少；仍需适配导航、资源、目录入口及源文件到页面的映射。 | 优先尝试。 |
| 构建期适配为临时站点输入 | 仅维护源文件；临时输入不可手工编辑 | 增加受测的适配器，但可隔离框架所需的元数据和路径规则；适配应保留内容语义。 | 直接读取不足时采用。 |
| MDX 成为设计正文主格式 | 仅维护 MDX | 交互组件表达力强；增加语法迁移、组件依赖和脱离站点后的阅读成本，并影响现有检查器。 | 不作为当前默认方案。 |
| Markdown 与 MDX 各写一份 | 两份正文需要持续协调 | 表现自由，但更容易出现内容漂移、审阅来源不明及遗漏更新。 | 不采用人工双份同步。 |

构建期适配不一定要生成 MDX。应优先输出目标工具支持的 Markdown、内容集合或渲染输入；确需 MDX 时再处理其解析差异。生成目录和构建产物不作为另一份可编辑、可提交的正文。

## 建议的内容与站点边界

以下布局用于说明职责，不是已确定的目录迁移方案：

```text
docs/、PRODUCT.md、GLOSSARY.md 等既有内容
              │
              │ 读取指定提交中的内容
              ▼
独立文档子项目
  导航与公开页面清单
  来源路径、页面 ID、URL 的映射
  元数据适配、Markdown 渲染与可选 MDX 页面
  主题、组件、资源处理
              │
              ▼
带来源信息的预览或正式文档产物
```

站点专用的排序、导航分组、短标题及稳定页面 ID 可以由正文旁的配置或站点清单维护。正文已有的标题、ADR 决策状态、主题 Lifecycle 和实现覆盖应读取原来源，避免在清单中再次维护同一事实。发现重复声明不一致时，应报告冲突，而不是静默选择一份。

同一设计在审阅预览和开发者文档中可以使用不同导航入口，但正文仍来自同一来源。用户指南面向任务和实际可用能力，可以有独立叙述；它与需求合同并非同一篇文章，不应机械复制或由 Spec 自动改写成“已经支持”的操作说明。以引用、适用范围和相应实现证据建立联系，重要变化时一起审查。

## 真正需要验证的同步边界

### 链接、锚点与资源

保留源文档中适用于仓库阅读的相对链接。构建时先相对于原源文件解析目标，再根据页面映射生成站点 URL；使用 Markdown 语法树处理链接和资源，不对全文执行字符串替换。

页面链接、目录链接、标题 fragment、图片及源码文件链接需要分别处理。目录入口可能需要从 README 映射为站点索引；中文、重复标题和已有显式锚点需要验证实际生成的 ID。没有对应站点页面的仓库文件，应按明确规则指向固定提交的源码或报告缺失，不能静默指向最新分支。

资源应随内容来源解析、收集和构建，验证站点根路径及类似 `/docs/` 的子路径。图片、搜索索引和附件也属于页面暴露范围；仅从导航隐藏页面不足以将它排除出发布产物。

### 图表与交互内容

Mermaid 代码块保留为唯一图表来源，由站点渲染或在构建时生成图片；不另画一份人工维护的同义图。ASCII 图可按原文保留，是否转换为图形应依据审阅收益决定。

确有交互需求的页面可以使用 MDX 组件，但规范行为和验收仍应可从设计正文中阅读。组件应引用同一份结构化数据或设计片段，而不是藏入另一套需求。只有一处使用的普通段落先保持完整文档引用，不急于建立片段抽取系统；必须复用时使用稳定标识并验证提取完整性。

### 来源身份与发布视图

设计预览应绑定实际构建的提交，记录正文、站点代码与页面清单的来源，提供固定提交的源码链接。PR 预览身份在构建外壳中展示，不需要把 PR 号、SHA 或文档修订标记写入每篇正文。

正式文档应说明对应的产品版本或开发分支；主分支文档不能自动代表已发布产品。设计审阅的候选页面和面向用户的正式页面可以共享正文与渲染链，但使用明确的页面范围和发布规则。若未来拆为不同仓库，应固定内容提交或制品身份，不能在两个仓库各取分支最新状态后声称来源一致。

### 自动检查与人工判断

自动检查适合证明路径存在、来源映射唯一、链接与锚点有效、资源齐全、构建成功及产物身份正确；既有 `REQ-*`／`VER-*` 检查继续针对原始 Spec 执行。复杂图表、页面阅读顺序和布局需要有针对性的渲染检查，不能用构建绿色代替。

单源构建消除的是同一正文在 Markdown 与网页之间的人工同步。PRD、Spec、ADR、实现覆盖和用户指南之间的语义一致性仍需人类审阅；不能承诺 CI 自动确认产品能力已经实现，或不同文章的描述在所有场景下等价。

## 后续最小验证问题

选型时用现有真实文档做一次有界验证，比先迁移所有内容更有信息价值。样本应包含根目录产品定义、中文架构及 Mermaid、含 frontmatter 的 ADR、带 `REQ-*`／`VER-*` 的 Spec、含显式锚点的合同，以及跨目录的操作文档。

需要确认：是否可以直接加载；如需适配，改动是否仅限元数据、路由与渲染；所有样本的正文、表格、代码和图表是否完整；相对链接、README 目录入口、中文与重复标题锚点是否有效；根路径与子路径下资源和深链是否可用；候选与正式视图是否都能追溯到正确来源。

本研究未安装站点依赖、构建框架样本或验证渲染结果，因而不宣称框架兼容性已通过。已确认的 Fumadocs 选型仍需在实现时验证依赖组合和实际内容；独立站点工程、单一正文来源和有界构建适配不依赖首期完成管理台嵌入。
