# 项目文档与独立文档站产品需求

## 问题与目标

Agent VM 已有客户端、控制服务、管理台、部署、镜像和工程治理材料，但内容分散在仓库入口、行为合同、操作说明和研究材料中。独立文档站的最小内容集不足以支撑完整的使用与开发阅读；项目级产品定义主要面向管理台，缺少整个产品的需求入口。

目标是让使用者知道怎样完成任务、部署者知道怎样安装和维护、开发者知道产品为何这样设计及如何参与开发。文档站直接展示唯一来源，并用确有价值的交互降低理解成本。长期行为合同及验收见 [SPEC](SPEC.md)，实际能力和未完成项见 [IMPLEMENTATION](IMPLEMENTATION.md)。

## 读者与阅读任务

| 读者 | 必须可以完成的阅读任务 |
| --- | --- |
| 客户端使用者与 Agent 的使用方 | 了解前提，安装和配置客户端，选择主机与镜像，申请环境、执行工作、续租、同步、取回结果、管理端口并释放环境，理解缓存不保证持久性。 |
| 管理台维护者 | 理解五个页面、资源和数据新鲜度，识别操作影响、权限、确认及审计，知道超时和结果未知时如何查证。 |
| 部署与运维人员 | 区分首次安装、旧状态迁移和普通升级；完成前提准备、配置、预检与验收，找到维护、观测、回滚及恢复边界。 |
| 开发者 | 理解产品范围、领域术语、当前架构、协议和实现状态；找到本地开发、测试、贡献、发布兼容及关键决定。 |

## 内容产品与组织

覆盖根文档、`docs/`、`deploy/`、`images/`、贡献和工程治理材料，逐项给出保留、补充、合并迁移、历史归档或仅供 Agent 的处置及理由。当前使用与开发所需正文在站内可读；ADR、历史提案通过有状态的索引访问，清楚区分历史与当前规则。Agent 指令、临时执行材料和私有运行记录不混入读者导航。

`PRODUCT.md` 是项目级唯一产品定义，说明用户、问题、主要场景、能力地图、边界和成功标准。复杂主题在现有 `docs/specs/<topic>/PRD.md` 展开产品需求；`SPEC.md` 继续负责可验证行为，`contracts/` 负责接口细则。不强制每个主题都有 PRD，不因补充 PRD 搬迁全部既有合同。

面向任务的指南归入 `docs/usage/`；首次使用、连接配置、日常工作、管理台、镜像和故障入口各有清楚职责。部署正文保留 `deploy/docs/`，镜像构建与资产说明保留 `images/README.md`，开发贡献复用 `CONTRIBUTING.md`。详细放置规则以 [文档组织与编写规范](../../README.md)为准，不在站点应用中复制规范正文。

## 表达与交互

默认使用 Markdown，并由站点提供目录、链接、代码复制、图表和其他阅读增强。MDX 只用于需要读者选择或操作的具体内容，保持唯一正文；展示组件复用同一份合同、配置或受控示例，不维护第二份参数定义。

连接指南说明 SSH 和 HTTPS 各自的配置、依赖和命令，并区分控制认证与来宾连接。可直接用 Markdown 分节呈现；只有场景切换明显帮助读者理解时才采用 MDX。若采用交互，示例使用占位值，不收集真实凭据、不连接真实服务、不执行管理动作，组件优先复用 Fumadocs/Radix。

导航按读者任务组织，文档站自身工程材料归入开发文档。历史材料可发现，但不与当前使用说明混为同一推荐路线。本文不要求建设独立审阅工作台、需求追溯产品或业务模拟器。

## 正确性与成功条件

指南以项目现有合同和运维资料为依据，清楚标明设计目标和历史说明。关键阅读路线必须有完整的步骤和参照入口，不能以占位文案验收。

成功需要三类证据共同成立：内容核对、全站展示与引用检查、负责人实际阅读。负责人走通首次使用、部署维护、理解设计三条路线，确认入口、正文和定位都可用；如果页面采用了交互，也检查它是否帮助阅读。

## 范围边界

本主题包含必要的站点内容适配、跨目录热更新、导航、引用、API/配置展示和验证。MDX 组件按内容需要采用，不设最低数量，不作为完成门槛。发现产品文档之间有矛盾时标明疑点与对应来源；产品实现审计和业务修复不属于文档整理。

管理台嵌入、生产与 Demo 嵌入、公开托管、在线批注、产品发布和现网操作仍不包含在本次文档整理中。交付与编排状态由独立运行账本管理，不写入本产品需求正文。
