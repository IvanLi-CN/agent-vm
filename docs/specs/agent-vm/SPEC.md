# Native Incus Agent VM

## Context and Scope

This topic defines a one-shot client and control process for session-owned Linux containers on a configured Incus host. The public repository documents the lifecycle contract and ships the implementation; deployments provide their own project, container image, network, address pool, storage path, state database and control address through explicit configuration.

The design excludes public brokers, arbitrary HTTP gateways, polling by the client, implicit keepalives, shared host workspaces, exported archives and guarantees that survive lease expiry. The target control environment contains one protected Go resident service per blue-green slot; its internal UDS API and scheduler are implementation boundaries, not a client surface. The built-in management console and direct Agent API are target surfaces for that active service through the project Caddy entry point, and neither may expose arbitrary internal control routes. The current checkout still exposes the existing protocol-4/UDS and SSH compatibility paths; the target OIDC, Caddy, browser API, direct Agent API and rqlite topology are not proof of an implemented or deployed listener.

The deployment topology is layered: the local Codex client reaches a configured Agent VM control endpoint; the control environment runs inside the observed CT109 LXC; the control environment owns session-scoped Incus system containers; and the physical or virtual source below CT109 is outside the verified public boundary. A control endpoint is an entry path, not evidence of the underlying host or its rebuild authority. The concrete address and live inventory remain in protected deployment records.

## Session and transport

Session-scoped requests carry a `session_id`; the sessionless read-only `admin-metrics` request omits it and rejects both `session_id` and `operation_id`. The CLI selects a session from explicit `--session-id` first and `AGENT_VM_SESSION_ID` second for session-scoped actions. A missing value returns `missing_session` before any remote write. Session identity is ownership metadata and is not an authentication mechanism. The client sends one versioned JSON request over the configured control path and emits one JSON response; diagnostics go to stderr. Format-1 client views use the legacy Bun control entry. Format-2 client views select the fixed `legacy-bun` or `go-request` transport; `go-request` retains SSH as a compatibility adapter while the remote Go request process sends the same body over the protected control UDS.

Protocol 4 is required by both client and control. Mutations include an operation ID and lease generation. The control persists requests and outcomes, rejects incompatible or conflicting retries, and never replays an uncertain native mutation automatically. The target direct HTTPS transport is `POST /agent/v1/control` with an opaque Bearer Token and the same protocol-4 body; the target unified service also exposes the independently versioned browser contract in [the management API](contracts/management-api.yaml) and [the Token API](contracts/token-api.md). Adding these target APIs does not change CLI protocol 4, and their presence in this specification does not assert that the current checkout serves them.

## Lifecycle

Each session owns at most one managed-container slot, including preparing, stopping, deleting and cached states. Every task records the pinned container-image fingerprint used to create its guest. Acquire creates or reuses a stopped cache only when that fingerprint still matches the current pinned image; a stale cache returns `cache_stale` before native effects, and an operator must explicitly destroy it before a new acquire creates a guest from the current image. Acquire records a new generation and waits for the container to be running and IPv4-ready within one bounded monotonic budget. If an unrelated lease-expiry cleanup briefly exposes a transitional native instance, acquire waits within a separate bounded 30-second admission-convergence budget, polling no more often than every 250 milliseconds, and keeps the same operation pending; only that exact transitional condition is retryable and all other unverified state fails closed. Lease expiry and release revoke access, remove only owned mappings and stop the guest before making the slot reusable. A stopped container root filesystem may remain as a disposable cache; no recovery guarantee is made.

A newly created guest receives its managed, task, session and generation ownership metadata in the native initialization request. A failed or uncertain initialization does not authorize claiming an existing unmarked instance. Recovery may reclaim a failed initialization with a confirmed missing instance only after same-session native workers are verified clear; a contextual native not-found result must identify the requested instance and project, and an uncertain or unrelated query failure is not proof of absence; ownership, generation or native-query uncertainty keeps the task and reservation. Cleanup of a present instance also waits for unresolved same-session workers before native mutation. A cached guest must carry the current generation; a verified previous-generation guest keeps its reservation until that generation discrepancy can be safely reconciled. Each acquire journals its durable task identity and generation before native work so recovery can distinguish a recreated session from an older operation. Verified independent acquire records may be reconciled while other tasks remain blocked, without reopening admission. An active acquire cannot be finalized by orphan recovery; a bound pending acquire must match that identity and generation. Recovery retains a verified pending destroy intent when the task is closing, subject to the same worker and ownership checks. Legacy unbound requests require a current or immediately preceding generation match. Legacy starting acquires may be finalized before transition only when all same-session pending operations are equally pre-transition, except that a finished older-generation acquire remains pending independently, and either their cached task retains the request generation with ownership and state verified, or no task or generation tombstone exists and native instance absence is confirmed. A previously blocked maintenance reconciliation may retry once after transitional tasks clear and its worker is verified absent. A superseded acquire, resize or restart may stop blocking admission only after a later successful same-session operation is confirmed by journal order and timestamps after the saved worker finished, the current cached task is verified stopped and owned, all saved worker identities are confirmed absent, and the control service cgroup and Incus background operations are quiescent. The original request and worker evidence remain recorded, and retries return an explicit unknown historical outcome without replaying the original native operation. Legacy worker records marked finished with an error require identity and process-group verification before recovery treats them as exited.

Renewal is explicit and bounded. Acquire, status, SSH, execution and transfer do not renew a lease. A changed generation or expired lease rejects late readiness and native results. Durable state, locks and timers make repeated requests idempotent without hiding partial cleanup.

Native process observation is race-tolerant: when a tracked process exits between `/proc` enumeration and identity reads, the controller treats it as gone and continues the normal bounded cleanup path. Linux worker identities without a process-group ID remain unverified and keep reconciliation blocked. Process-group discovery remains fenced by the worker PID start time; after the root disappears, only members observed while that root identity was present or descendants of an observed member may be retained, and an unexpected same-group member keeps state unverified. A normally reaped root with a confirmed-empty group is accepted; an observed group that remains or cannot be verified keeps state unverified. Bounded cleanup performs a final observation after an empty scan and confirms kernel process-group absence before success. When a worker root disappears, cleanup must still inspect its process group before declaring the worker gone, including a kernel group-presence check after a procfs snapshot. Group cleanup keeps the root pidfd as an identity anchor, rechecks the root identity after every non-atomic process-table scan, signals verified members before the root, and only admits newly observed root-less descendants through an already verified member; a first root-less scan never claims an unanchored numeric process group, and a reused numeric PID or process group never becomes an ownership claim. Zombie-only snapshots are refreshed and still pass through the kernel group-presence probe; only identity-verified root or members may be reaped, so a group is non-live only after both procfs and kernel evidence agree. A native worker start is journaled as `starting` with an explicit unattempted marker before admission and records a one-shot start attempt for each admission; inactive workers with an explicit unattempted marker and no identity may be recovered as exited, while legacy records without that marker remain unverified; every later start under the same operation re-arms that durable barrier, and a confirmed pre-spawn failure records `exited` so the operation can be retried. Nested maintenance recovery may bypass only the active coordinator's unattempted preparation marker; an attempted or identity-bearing worker remains blocking. An attempted but unjournaled start remains blocked. A native worker completion with an error remains journaled as running so startup reconciliation cannot treat uncertain ownership as finished; later native worker starts under that operation or its session are refused until the identity is reconciled. Missing native instances may only finalize destroy after all same-session worker journal entries are verified clear, including the destroy worker itself and pending acquire journals that already record an attempted worker. A pending destroy with an absent task requires confirmed native absence, a terminal worker record and the same generation in the task or retained tombstone; missing native access, an active request, an unverified worker or generation uncertainty keeps it pending. Once reconciliation verifies the identity has exited, recoverable maintenance operations may retry. Without delegated cgroup tracking, the isolated process group is also the ownership boundary for reparented descendants. Other process-table read errors remain failures.

## Access and isolation

The deployment configuration supplies the control address and host port range. Proxy NAT uses the configured host address, leased port and fixed guest address. SSH keeps host-key verification enabled with explicit identity and known-host files. The managed Incus project must allow the required proxy devices, and the configured ACL must prove peer and host isolation before admission. Exact conntrack entries are removed during mapping cleanup.

## Capacity and resizing

Capacity observations are limited to the configured Incus pool filesystem and visible control-environment CPU and memory boundaries. External storage probes and infrastructure-manager inspection are unsupported. CPU and memory allocation ceilings use separately configurable overselling ratios; stopped caches consume disk only. New demand is refused when capacity measurements are missing or invalid, when the logical reservation ceiling is exceeded, when disk admission fails, while draining, or when a new native boot would run during verified severe CT-local CPU scheduler pressure. The approved overcommit deployment profile sets `cpu_startup_pressure_full_avg10_percent` to `50`; the CPU startup guard applies only when projected CPU allocation exceeds CT-visible CPU capacity and verified `full.avg10` reaches that threshold. It does not change the logical CPU ceiling or stop an effective lease. Low CT memory headroom is an observation and warning under reservation-only memory admission; it does not reduce logical remaining memory or reject a request within the configured ceiling. Existing lease queries, retrieval, renewal and release remain available during pressure.

Rootfs allocation changes require an explicit restart allowance and grow only. Container rootfs growth is an independent post-check: it verifies the Incus root device and the container-visible rootfs capacity against the requested allocation, treats a rootfs already at least 95% of the requested capacity as an idempotent success, and fails closed when the selected storage/profile cannot expose that evidence. The old reservation remains until both the Incus root device and container rootfs capacity are verified. A single bounded convergence retry is allowed for the documented native balloon timeout; no polling loop or third attempt exists. Partial native or rootfs growth changes retain conservative reservations and a structured recovery state.

## Reclamation and operations

Manual garbage collection is dry-run by default and selects only stopped managed caches with no effective lease and confirmed access cleanup. The age timer and capacity admission may use different bounded selection policies, but neither can delete a valid lease, transition, resize target or unknown resource. Infrastructure operations require a separate explicit authorization and use the same configured paths and identity checks.

## Control-plane releases and compatibility

The Go control service remains the sole authority for Incus operations, durable lifecycle state, lease generations, capacity admission, native mappings, observation snapshots and maintenance. Its in-process scheduler owns lease expiry, startup compensation, bounded retries and cache age-GC; systemd starts and restarts the service but is not the durable scheduler. The local `agent-vm` CLI remains a versioned request client; publication, update and rollback are operator-owned deployment actions and are not public CLI lifecycle commands. Unattended control-plane updates are disabled by default.

A control-plane release is a logical compatibility unit containing the local client, the compatibility bridge or Go control binary, systemd unit assets, the fixed Caddy-facing service assets, and a release manifest. Production format 3 records one product SemVer, exact `source_revision`, target/toolchain, artifact checksums and modes, protocol 4, and per-operation request/response/semantic compatibility in each supported direction. A management-enabled package uses format 4, which adds declared durable state read/write capabilities, OIDC/Token/API compatibility and the embedded management assets. Formats 1 through 3 remain read-only migration and necessary rollback inputs; they are not new management-enabled production output. Deployment configuration, credentials, connection material, state database and WAL/journals, locks, Incus container data, and guest images are outside the release.

Compatible operations may continue across different release revisions with a structured warning. Compatibility is not inferred from parseability: an unsupported action, incompatible schema or semantic change, invalid checksum, or incompatible protocol MUST fail before any durable or native effect. A compatible evolution preserves the established protocol contract; a breaking evolution may require a new protocol and an explicit client update.

Management state uses versioned capability markers. A release may activate against a database only when it declares support to read and write every marker present. Formats 1 through 3 imply support for the pre-management state only. An incompatible package rollback is refused before pointer activation or service start; the database is never downgraded to make an older package appear compatible.

## Management console and API

The console manages existing Agent session VMs, managed images, capacity, operation history, audit and fixed system-maintenance actions. It has no manual VM creation, generic Incus, host/PVE, shell or Web terminal surface. Its five pages are Overview, VMs, Images, Operations & Audit, and System. The first authenticated view is Overview.

The target browser API is same-origin `/api/v1` and is independent of protocol 4. OIDC Authorization Code + PKCE with `code_challenge_method=S256` only, exact issuer/subject identity, secure browser sessions, exact Origin validation and session-bound CSRF protection are mandatory for that target. The target direct Agent API is `/agent/v1/control` and requires an opaque Bearer Token; it never accepts a browser Cookie. If any required OIDC, Token, origin or resource-limit configuration is incomplete, the target listener stays disabled. The [management contract](contracts/management-api.md), [Token API contract](contracts/token-api.md), [Agent API contract](contracts/agent-api.md) and [OpenAPI document](contracts/management-api.yaml) define the target wire shapes and deployment inputs; current implementation evidence remains limited to the existing compatibility surfaces.

The UI supports `zh-CN` and `en`. A saved preference takes priority over browser language; English is the fallback. All interface and accessible copy is localized. Identifiers, fingerprints, stable error codes and user-authored reasons remain unchanged. The API returns locale-neutral values, preserves observation freshness and represents unknown measurements as unknown rather than zero.

Ordinary users can access only their own sessions and Tokens, and every Agent request rechecks Token owner, scope, session ownership, generation and expiry/revocation. Administrator mutations use a UUID operation identity, an operator reason and a resource version; VM actions also carry the exact session generation. Sensitive actions use a preview-bound confirmation token and the unified service revalidates all preconditions before effects. The operation and audit APIs preserve issuer/subject actor, target, reason, phase and outcome. An uncertain result remains queryable and is never automatically replayed with a new operation identity.

Image import is limited to configured trusted sources and size-bounded local Incus container packages. Integrity and Agent VM suitability are distinct checks. A selected default must be verified, except that the pre-existing configured default is preserved as a visible legacy-compatibility default until an administrator chooses a verified replacement. Existing tasks and caches retain their pinned image fingerprint. The authority serializes default selection and reference changes; the default affects new sessions only, and any default, active, cached, releasing, pending-creation or verification reference blocks deletion.

The target first management state migration is additive and transactional. It preserves tasks, generations, leases, ports, reservations and protocol-4 journals. SQLite remains the single writer until a drained, verified one-time import makes rqlite the shared authority; dual writes, shared SQLite file access and database downgrade are forbidden. Critical reads use linearizable consistency and cross-row changes use one rqlite transaction. The state-capability markers, legacy-default seeding, installer preflight and full-package rollback rules are defined in the [management contract](contracts/management-api.md), [state migration ADR](../../adr/0044-agent-vm-state-migration-to-rqlite.md) and [release contract](contracts/release.md). This is a target migration contract, not evidence that the current checkout has performed it.

Remote control-script and unit publication MUST use the configured control SSH entry, an operator-only identity or narrowly scoped root-owned deployment wrapper, a private staging area, and atomic activation. It MUST NOT add an sshd, HTTP gateway, PVE path, or Agent VM guest permission. Remote publication is activated and verified before the local client is updated; a local-only client update does not require drain.

Remote publication MUST enter admission drain before activation, block new acquisition and restart admission, keep expiry/reconciliation/cache-cleanup timers available, and allow in-flight requests to finish without force-killing them. It MUST wait for pending operations and task transitions to converge, verify health, reconciliation, and timer state, and exit drain only after successful validation through the active release transaction's release-scoped session; a browser maintenance request MUST NOT reopen admission. The first management-aware release MUST be able to claim an ownerless drain left by the previous protocol-4 controller, while a different release or browser request MUST NOT replace an active release owner. Queued management work that has not crossed the native-effect barrier remains retryable and MUST be durably fenced from starting while drain is active. A pre-activation failure leaves the current release untouched. A post-activation health failure permits one bounded rollback to the previous verified release; an unsuccessful rollback keeps admission drained and MUST NOT rewrite state, generations, or uncertain operations. At least the current and previous verified releases MUST be retained with their manifests and checksums.

## Requirements

### REQ-AGENT-VM-010 - Layered provenance

The public contract MUST distinguish the Codex client, configured control endpoint, CT109 LXC, Incus system container, and unknown underlying hosting source. It MUST NOT turn a configured address, CT identifier, or Incus identity into a claim about the next lower layer, and it MUST keep private deployment addresses and inventories outside the repository.

### REQ-AGENT-VM-011 - Rebuild and recovery fencing

Recovery MUST preserve the state database and WAL/journals, operation and audit records, generations, configuration, protected recovery copies, native timer assets, and Incus container data. It MUST restore matching components under drain, reconcile durable records against native ownership and generations, and keep admission closed when state, provenance, capacity, or native identity is missing or inconsistent. It MUST NOT invent operation IDs, reset generations, replay uncertain native effects, or perform broad cleanup.

### REQ-AGENT-VM-012 - Sparse disk failure boundary

Disk admission MUST account for the configured CT-local Incus pool filesystem, request cost, watermarks, and durable reservations without claiming a full physical reservation for every configured container rootfs limit. Control-plane state and container data MUST be treated as separate logical failure domains; ENOSPC or I/O failure MUST preserve conservative state and refuse unsafe new admission without evicting an effective lease.

### REQ-AGENT-VM-013 - Observability provenance

Operational dashboards MUST distinguish CT filesystem capacity, transient image staging, physical Incus pool usage, guest rootfs allocation, and native admission state. They MUST NOT infer an authoritative native limit from an unset Incus project quota or draw a limit line for a missing or `-1` source. The dashboard contract MUST expose failure phase, image-unpack failures, admission state and scrape freshness so an ENOSPC boundary can be identified without host-manager access. The public repository MUST ship a sanitized, parameterized dashboard baseline and validation path; deployment-specific rendered files, datasource identities, controller jobs and collector paths remain deployment-owned.

### REQ-AGENT-VM-014 - Control-plane update authority

Control-plane publication, update, and rollback MUST remain operator-owned deployment actions. The public `agent-vm` CLI MUST remain a lifecycle/request client and MUST NOT acquire Incus/PVE authority, expose a public self-update command, or become a second control plane. The Go `serve` process MUST remain the sole live control authority; the legacy Bun control process is permitted only as a verified compatibility release or forwarding bridge and MUST NOT run concurrently against live state.

### REQ-AGENT-VM-015 - Method-level compatibility

A release manifest MUST declare protocol, request/response schema, semantic compatibility, and direction for each supported operation. A compatible operation MAY continue across release revisions with a structured warning. An unsupported action, incompatible schema or semantic change, invalid artifact checksum, or incompatible protocol MUST be rejected before any durable or native effect.

### REQ-AGENT-VM-016 - Publication transaction and rollback

Publication MUST stage and verify an explicit release before drain, enter drain before remote activation, preserve in-flight operations and maintenance timers, wait for pending operations and task transitions to converge, atomically activate artifacts, and verify health, reconciliation, and timer state before reopening admission. A pre-activation failure MUST leave the current release untouched. A post-activation health failure MAY perform one bounded rollback to the previous verified release; failed rollback MUST keep admission drained without rewriting state, generations, or uncertain operations.

### REQ-AGENT-VM-017 - Release scope and permission boundary

A control-plane release MUST contain the local client, remote control script, systemd assets, release metadata, and exact artifact checksums, while excluding deployment configuration, credentials, connection material, state databases, locks, Incus container data, and guest images. Publication MUST use the configured control entry with operator-only or narrowly scoped root-owned deployment authority and MUST NOT add PVE, host, guest, extra SSH, HTTP, or gateway access. Unattended control-plane updates MUST remain disabled by default.

### REQ-AGENT-VM-018 - CPU startup pressure boundary

The controller MUST observe CT-local CPU PSI separately from logical CPU reservation. When a new acquire, cached resume, restart-capable resize, or explicit restart would project CPU allocation above CT-visible CPU capacity and verified `full.avg10` meets the configured startup-pressure threshold, it MUST refuse the native boot with structured `resource_pressure` evidence before stopping or starting an existing guest. The guard MUST NOT change logical CPU allocation ceilings, stop an effective lease, or block read, renewal, retrieval, release, or live memory-only resize; missing CPU PSI MUST remain an explicit observation failure rather than a fabricated zero.

### REQ-AGENT-VM-019 - Capacity and inventory observability

The read-only observation contract MUST distinguish logical reservation composition, CT-visible capacity, runtime pressure, physical disk headroom, native admission state and per-task lifecycle state. It MUST expose `some.avg10`, `full.avg10`, the configured startup threshold and startup-blocked state without treating PSI as CPU utilization or logical remaining capacity. The approved overcommit deployment profile MUST configure a 50 percent full-pressure threshold while retaining the compound projected-capacity gate.

The deployment observation surface MUST provide separate capacity/admission and inventory/operations views. The capacity view MUST show allocated, reserved, allocated-and-reserved, remaining, limit and CT-visible capacity where authoritative, plus task-state counts and explicit snapshot estimates for logical and currently startable default-container slots. The inventory view MUST cover all managed task states, use bounded fields, remove stale rows, and avoid raw errors, credentials and deployment paths. A missing or `-1` native slot limit MUST remain absent; a derived slot estimate MUST NOT be labelled as an authoritative slot limit.

The deployment scrape bridge MUST schedule `admin-metrics` and `admin-status` as independent observation lanes. A pending or failed inventory read MUST NOT remove the latest valid capacity metric families, and a pending or failed capacity read MUST NOT retain task rows from an unsuccessful inventory scrape. A retained source snapshot MUST keep its original observation timestamp and expose source-specific health or freshness failure; the bridge MUST NOT replace unavailable values with fabricated zeroes.

### REQ-AGENT-VM-020 - Authenticated management boundary

Each blue-green slot MUST run one Go/Gin Agent VM service that serves the fixed static Web assets, OIDC callback, same-origin management API and `/agent/v1/control`; the design MUST NOT add an independent Web process, Forward Auth identity header, management UDS, router, Web/BFF, native service or public TCP bypass. Caddy MUST perform only TLS and fixed-path active-slot routing. The unified service MUST enforce bounded methods/paths/inputs, OIDC/session/Token authorization, Origin/CSRF, ownership, generation and journal checks, and MUST leave the listener disabled when required OIDC, origin, Token, upload or staging configuration is incomplete.

### REQ-AGENT-VM-021 - Management API and localized interface

The management console MUST expose only the same-origin `/api/v1` surface defined by the OpenAPI contract. It MUST reject unknown fields and unsupported actions, use bounded cursor pagination, preserve exact byte and generation values, return structured field-whitelisted errors, and expose source freshness and unknown values without coercing them to healthy zeroes. The UI MUST support `zh-CN` and `en` with saved choice, browser-language and English-fallback priority; accessible names, confirmations and errors MUST be translated while technical identifiers and user-entered reasons remain unchanged.

### REQ-AGENT-VM-022 - Managed actions and audit recovery

Every mutation of an existing management resource MUST carry a UUID operation ID, a bounded non-empty reason and the current target version; every durable create or Token issuance MUST carry a UUID operation ID and canonical retry identity; VM actions MUST also carry the expected generation. Administrator-sensitive submission MUST use a confirmation token bound to the authenticated subject, exact target, action, parameters and target version, and the authority MUST recheck authorization and state before effects. Identical operation retries MUST resolve to the same durable operation; a conflicting reuse MUST fail. A Token create is idempotent at the durable operation and metadata layer: the first transaction atomically consumes the one-time plaintext disclosure latch, only that response may carry the bearer, and later or concurrent retries return the same `token_id`/metadata without plaintext. Uncertain native outcomes MUST remain queryable and MUST NOT be replayed automatically. Audit records MUST preserve actor, reason, target, phase and outcome without exposing raw command diagnostics, credentials or private paths.

### REQ-AGENT-VM-023 - Managed image safety and session pinning

Managed images MUST use immutable fingerprints, allowlisted source identities, bounded local package uploads, independent integrity and suitability results, and explicit reference counts. The configured legacy default MUST be preserved during migration and shown as unverified until replaced; only a fully verified image may be selected through the management API. Default selection MUST affect new sessions only. Existing tasks and caches MUST retain their exact fingerprint. Default, active, cached, releasing, pending-creation and verification references MUST block deletion, with reference checks serialized against image operations.

### REQ-AGENT-VM-024 - Management state and rollback compatibility

Management schema changes MUST be additive, transactional and recorded by versioned state-capability markers. Migration MUST preserve task identity, generations, leases, ports, reservations and existing protocol-4 journal state. A package may activate only when it declares support to read and write every capability marker in the state database. Packages without a capability declaration MUST be treated as supporting pre-management state only. An incompatible rollback MUST be rejected before changing active package pointers or starting the target; databases MUST NOT be downgraded or recreated to force compatibility. Protocol 4 and existing CLI request/response behavior MUST remain unchanged.

### REQ-AGENT-VM-025 - OIDC principal and browser session identity

The browser login MUST use OIDC Authorization Code + PKCE with `code_challenge_method=S256` only, one-time `state`, `nonce`, protected code verifier, exact redirect URI, a short-lived browser-bound login cookie and bounded expiry. The service MUST validate the configured discovery issuer, exact ID Token `iss`, `aud`/`azp`, signature/JWKS, `exp`, `iat` policy, authorization-code exchange and nonce before creating a session. Service and proxy access logs MUST omit callback query strings and `Referer`, and application logs MUST NOT retain OIDC code, state, nonce or verifier values. The durable principal MUST be the exact case-sensitive `(issuer, subject)` pair; email, display name, group claims and forwarded identity headers MUST NOT establish ownership. A replayed, expired, cross-browser or unverified callback MUST be rejected, and a successful login MUST NOT implicitly grant administrator capability.

### REQ-AGENT-VM-026 - User ownership, Token API and Agent API

Ordinary users MUST be restricted to their own sessions and opaque Agent Tokens. Token metadata MUST bind one exact `(issuer, subject)` owner, an explicit session set, scopes, expiry and revocation state; the plaintext MUST be returned only once, while the service stores only a validation digest and a one-time disclosure state. Token creation MUST require an operation ID and canonical request identity. A same-principal retry or concurrent request MUST return the durable operation's `token_id`, metadata and disclosure state without reissuing plaintext; after a lost response, the owner MUST query the original operation, confirm the token ID, revoke that token explicitly and create a replacement with a new operation ID. Token revocation MUST commit before acknowledgment and Agent authorization MUST observe the revocation with a linearizable read. The `agent:observe_admin` scope MUST be issuable only to a principal with the explicit administrator observation capability. `POST /agent/v1/control` MUST accept only a valid Bearer Token and the existing protocol-4 body, and MUST recheck Token expiry/revocation, scope, session ownership, generation, operation ID and request digest for every request. A user MUST NOT obtain another user's resources through guessed identifiers, filters or modified JSON, and a sessionless administrative observation MUST require an explicit administrator scope.

### REQ-AGENT-VM-027 - Administrator sensitive actions and audit

Administrator capabilities MUST be mapped to an exact `(issuer, subject)` pair and MUST NOT be inferred from login, email or group claims. Sensitive actions MUST require an explicit capability, a non-empty bounded reason, an impact preview and a one-time confirmation token bound to the actor, exact target, parameters, target version and generation. The unified service MUST recheck authorization and state before native effects. Accepted, rejected, succeeded, failed and outcome-unknown attempts MUST be auditable with issuer/subject, reason, operation ID, target, phase, result and safe error code, without Token values, OIDC codes, credentials, raw command output or private paths. An unbound historical owner MUST remain inaccessible until an administrator explicitly maps it to one exact principal with the same reason/confirmation/audit rules.

### REQ-AGENT-VM-028 - Conservative SQLite-to-rqlite migration and atomic concurrency

SQLite MUST remain the sole writer until a state-write fence rejects new browser/API/Agent durable mutations, pauses scheduler/reconciliation/timer durable writes, drains in-flight transactions and native workers, and requires each native worker to finish with a durable result under its original operation ID plus verified process-group, PID-identity and Incus-operation quiescence. A pending/unknown native result, an active worker or unverified quiescence MUST block final export; migration MUST NOT merely record it and continue. Migration MUST preserve protocol 4, schema, generation, `state_epoch`, operation journal, audit, session, Token and capability semantics; it MUST NOT dual-write, open a shared SQLite file from both slots, reverse-sync guessed state, downgrade schema or recreate state for rollback. After cutover, rqlite MUST be the sole shared authority; critical ownership, lease, generation, journal, Token-revocation, capability and epoch reads MUST use linearizable consistency, and cross-row compare-and-act changes MUST use one rqlite transaction with conditional updates or unique constraints. If rqlite recovery is needed, a verified post-cutover backup/snapshot is required unless evidence proves zero post-cutover writes and effects; otherwise the service MUST stay fenced for owner-authorized journal/native reconciliation. Native unknown outcomes MUST remain pending and MUST NOT be replayed with a new operation ID.

### REQ-AGENT-VM-029 - Blue-green compatibility window

The release contract MUST retain the current and previous verified package and fixed static resources for at least one hour of API/state compatibility. Each release MUST declare protocol, request/response/semantic windows, OIDC/Token/management API compatibility and state capability read/write sets. The active link MUST change atomically only after target readiness and shared-state checks pass; Caddy MUST NOT replay writes. A slot or rollback target that cannot read and write every present capability MUST be rejected before activation, and a browser asset outside the compatibility window MUST receive an explicit refresh result rather than silently using mismatched API or state semantics.

## Synchronization and retrieval

The TypeScript/Bun synchronization helper transfers tracked, unignored worktree files to its own guest source directory and atomically replaces only helper-owned content. Git selection, manifests and native filesystem access preserve byte paths, symlink targets, modes and hashes; unsupported local root-path representation fails explicitly. It rejects submodules, symlink parents, reserved ownership filenames and unsafe names before transfer. The guest transaction is an in-memory Bun action guarded by the managed image's runtime/native prerequisites and an external execution deadline; missing Bun or atomic capability fails closed. Native locks, exclusive preparation, baseline identity comparison, fsync and atomic directory exchange preserve the current source and adjacent results across conflicts and failures. An uncertain commit keeps its source marker and precise recovery record and returns exit 75 rather than an inferred rollback. The [CLI contract](contracts/cli.md#source-synchronization-transaction) defines execution bounds, ownership and recovery. Export streams a tar archive directly to the caller and does not create a server-side archive.
