# Agent VM Control-Plane Release Contract

This contract describes the manual release boundary for the Agent VM client and control environment. It is not a public `agent-vm` lifecycle command and it does not grant access to PVE, a host manager, an Incus policy API, a guest, or an HTTP gateway.

## Release manifest

The operations-side parser in [`release_manifest.py`](../../../skills/agent-vm-ops/scripts/release_manifest.py) is the only authoritative manifest validator. A complete `release-manifest.json` contains `format: 1`, `release_id`, a 40-character lowercase Git `source_revision`, `protocol: 4`, a non-empty `artifacts` list, an `actions` object, and a matching `client_view`. `release_id` equals `source_revision`.

Each artifact declares only a relative path, role, exact SHA-256 of its bytes, and numeric mode. The artifact path must resolve to a regular file inside the release root; absolute paths, parent traversal, symlinks, non-regular files, manifest self-checksums, and mode or checksum mismatches fail closed. The release contains the local client, one-shot control process, support parser, and fixed systemd assets. It excludes configuration, credentials, SSH material, state databases and WAL/journals, locks, Incus VM data, and guest images.

Each action declares `request.schema`, `request.semantic_revision`, `response.schema`, `response.semantic_revision`, and explicit `client_to_control` and `control_to_client` objects with `schema_min`, `schema_max`, `semantic_min`, and `semantic_max`. JSON parseability is not compatibility evidence. The control process checks protocol, action, request window, response window, and all artifact bytes before a journal record, native handler, or timer preemption.

The client reads only its local sidecar client view. A missing sidecar selects the explicit `legacy-protocol-4` capability and returns a structured warning; it does not silently claim a current release. A present but malformed, path-invalid, mode-invalid, or checksum-invalid sidecar fails closed. A compatible action across different revisions succeeds with a top-level warning, and write-operation replay preserves that warning.

## Wrapper boundary

The operator pre-installs a root-owned narrow wrapper at the fixed path `/usr/local/sbin/agent-vm-release-wrapper` with a protected deployment configuration. Its control target is fixed at `/opt/agent-vm-native/agent_vm_control.py`, its systemd target directory is fixed at `/etc/systemd/system`, and its activation fence is fixed at `/run/agent-vm-native/release-activation.fence`; the wrapper configuration cannot redirect these targets. Its fixed actions are `stage`, `verify`, `activate`, `rollback`, and `status`. Callers provide only a transaction/release identity and the structured action; the wrapper does not accept arbitrary destinations, shell commands, configuration paths, state database paths, or VM paths.

`stage` reads a private bundle from standard input and extracts regular files only into transaction staging. It rejects absolute or parent-traversing names, symlinks, hard links, devices, duplicates, and oversized members. `verify` checks the manifest, exact bytes, regular-file owner and mode, Python syntax, fixed systemd unit names and canonical bytes, and the allowed artifact set. `activate` requires a verified transaction and admission drain, creates the fixed activation fence before the drain check, re-verifies retained current and previous releases, atomically retains the current and previous release pointers, installs only the fixed client, control, support, manifest, and unit targets, and may run `systemctl daemon-reload`; it never stops or disables a timer. `rollback` verifies the previous retained release, rejects stale transactions, permits one automatic attempt per transaction including an interrupted activation record, and never rewrites durable lifecycle state, generations, or uncertain operations.

## Publisher transaction

The manual publisher in [`agent_vm_release.py`](../../../skills/agent-vm-ops/scripts/agent_vm_release.py) implements `build`, `verify`, `publish`, and `rollback`. `build` copies only the fixed artifact set, client sidecar, and manifest into a tar bundle. `verify` checks the same release contract locally. `publish` verifies locally, stages and verifies remotely, enters drain through the existing one-shot control request path, and polls `admin-metrics` at most 1 second apart for the default 300-second convergence budget. It does not stop or disable maintenance timers, kill in-flight operations, or invent a replacement operation ID. The publisher always invokes the fixed remote wrapper `/usr/local/sbin/agent-vm-release-wrapper` and fixed remote control path `/opt/agent-vm-native/agent_vm_control.py`; the legacy `--wrapper` option is optional and only accepts that exact value.

After convergence, the publisher activates the verified remote release and checks `doctor`, `admin-metrics`, pending operations, task transitions, and timer/reconcile health. A pre-activation failure keeps the current release active and drained. A post-activation health failure permits one rollback attempt; a successful rollback is revalidated before drain exit, while a failed rollback keeps admission drained. Only after remote health succeeds does the publisher atomically install and self-check the local client. The client and sidecar pair uses a private durable recovery marker so an interrupted two-file install restores the previous pair before a later publish. A local client failure preserves the old client, reports a structured warning, does not roll back the healthy remote release, and does not reopen drain. Manual rollback verifies the supplied previous bundle, rolls back the remote transaction, installs that same local client pair, and exits drain only after both sides are healthy. Complete publication exits drain last.

The default publisher timeout is 300 seconds and the default poll interval is 1 second. Operators may lower those values but cannot exceed the timeout or poll safety bounds. Old releases are retained; deletion, automatic updates, resident brokers, and deployment inventory management are outside this contract.

## Public and private records

Public manifests, tests, and documents contain only relative source paths and neutral deployment placeholders. The live SSH alias, identity, credentials, release root, wrapper configuration, target paths, state database, timer inventory, and controlled staging observations remain operator-owned records outside this repository.
