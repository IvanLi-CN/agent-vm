# Agent VM Control-Plane Release Contract

This contract describes the manual release boundary for the Agent VM client and control environment. It is not a public `agent-vm` lifecycle command and it does not grant access to PVE, a host manager, an Incus policy API, a guest, or an HTTP gateway.

## Release manifest

The Python release tools use [`release_manifest.py`](../../../../skills/agent-vm-ops/scripts/release_manifest.py) for bundle and policy validation, while the Bun controller uses [`release-manifest.ts`](../../../../skills/agent-vm-ops/scripts/release-manifest.ts) to validate its runtime manifest and artifact bytes. A complete `release-manifest.json` contains `format: 1`, `release_id`, a 40-character lowercase Git `source_revision`, `protocol: 4`, a non-empty `artifacts` list, an `actions` object, and a matching `client_view`. `release_id` equals `source_revision`. Their fixed artifact policies require the same complete Bun client package. The publisher and protected wrapper remain Python release tools; they package, verify and install Bun entrypoints without a Python client fallback. [Implementation coverage](../../project-foundation/IMPLEMENTATION.md#agent-vm-client-behavior-evidence) distinguishes isolated package/transaction evidence from Linux/image and publication acceptance.

Each artifact declares only a relative path, role, exact SHA-256 of its bytes, and numeric mode. The artifact path must resolve to a regular file inside the release root; absolute paths, parent traversal, symlinks, non-regular files, manifest self-checksums, and mode or checksum mismatches fail closed. The Bun client package requires `agent_vm.ts` and `sync_worktree.ts` at mode `0755`, and `byte-fs.ts`, `client-io.ts`, `client-release.ts`, `client.ts`, `guest-source.ts` and `sync-native.ts` at mode `0644`. A complete release must carry that package alongside `agent_vm_control.ts`, `release_manifest.py`, the controller TypeScript support modules including `guest-root-growth.ts`, and the fixed systemd assets. It excludes configuration, credentials, SSH material, state databases and WAL/journals, locks, Incus VM data, and guest images. Restoring a Python client alongside the Bun entrypoint is not a compatibility strategy.

Each action declares `request.schema`, `request.semantic_revision`, `response.schema`, `response.semantic_revision`, and explicit `client_to_control` and `control_to_client` objects with `schema_min`, `schema_max`, `semantic_min`, and `semantic_max`. JSON parseability is not compatibility evidence. The control process checks protocol, action, request window, response window, and all artifact bytes before a journal record, native handler, or timer preemption.

The client reads only its local sidecar client view. Its exact top-level fields are `format`, `release_id`, `source_revision`, `protocol`, `client_artifact`, `client_dependencies` and `client_view`. `client_artifact` identifies `agent_vm.ts` with role `client`; `client_dependencies` lists the other seven fixed client files with role `support`. Each entry has exactly `name`, `path`, `role`, `sha256` and `mode`, with basename-only paths beside the sidecar. Missing, duplicate, extra or changed dependencies fail before SSH. The view contains the complete fixed action set and explicit request/response compatibility windows. A missing sidecar selects the explicit `legacy-protocol-4` capability and returns a structured warning; it does not silently claim a current release. A present but malformed, path-invalid, mode-invalid, or checksum-invalid sidecar fails closed, including an old Python-only sidecar. A compatible action across different revisions succeeds with a top-level warning, and write-operation replay preserves that warning.

## Wrapper boundary

The operator pre-installs a root-owned narrow wrapper at the fixed path `/usr/local/sbin/agent-vm-release-wrapper` with a protected deployment configuration. Its control target is fixed at `/opt/agent-vm-native/agent_vm_control.ts`, its control interpreter is fixed at `/usr/local/bin/bun`, its systemd target directory is fixed at `/etc/systemd/system`, and its activation fence is fixed at `/run/agent-vm-native/release-activation.fence`; the wrapper configuration cannot redirect these targets. Its fixed actions are `stage`, `verify`, `activate`, `rollback`, and `status`. Callers provide only a transaction/release identity and the structured action; the wrapper does not accept arbitrary destinations, shell commands, configuration paths, state database paths, or VM paths.

`stage` reads a private bundle from standard input and extracts regular files only into transaction staging. It rejects absolute or parent-traversing names, symlinks, hard links, devices, duplicates, and oversized members. `verify` checks the manifest, exact bytes, regular-file owner and mode, compiles Python support artifacts, transpiles every manifest-listed TypeScript artifact as data with the fixed `/usr/local/bin/bun` Bun transpiler, verifies fixed systemd unit names and canonical bytes, and enforces the fixed artifact set. It never imports or executes candidate TypeScript during syntax verification. `activate` requires a verified transaction and admission drain, creates the fixed activation fence before the drain check, re-verifies retained current and previous releases, atomically retains the current and previous release pointers, installs only the complete fixed Bun client package, controller, support, sidecar, manifest, and unit targets, and may run `systemctl daemon-reload`; it does not stop or disable a timer. `rollback` verifies the previous retained release with the same artifact, Python, TypeScript, and systemd checks, rejects stale transactions, permits one automatic attempt per transaction including an interrupted activation record, and never rewrites durable lifecycle state, generations, or uncertain operations. Activation snapshots the former fixed `agent_vm.py` and `agent_vm_control.py` targets when present, removes those retired executables after installing the Bun package, and restores their exact bytes, owner and mode if activation fails. It never runs them or adds them to a release.

## Publisher transaction

The manual publisher in [`agent_vm_release.py`](../../../../skills/agent-vm-ops/scripts/agent_vm_release.py) implements `build`, `verify`, `publish`, and `rollback` for the complete fixed Bun artifact policy and derived dependency-hashed sidecar. The local sequence is `python3 skills/agent-vm-ops/scripts/agent_vm_release.py build --source-root <source> --output <bundle>`, `python3 skills/agent-vm-ops/scripts/agent_vm_release.py verify --bundle <bundle>`, then `python3 skills/agent-vm-ops/scripts/agent_vm_release.py publish --bundle <bundle> --control-host <configured-alias> --client-target <local-package-directory-or-agent_vm.ts>`. Publication must preserve local verification, remote staging/verification, drain through the client's `bun /opt/agent-vm-native/agent_vm_control.ts` request path, and `admin-metrics` polling at most 1 second apart for the default 300-second convergence budget. It must not stop or disable maintenance timers, kill in-flight operations, or invent a replacement operation ID. The fixed remote wrapper remains `/usr/local/sbin/agent-vm-release-wrapper`, the remote controller target remains `/opt/agent-vm-native/agent_vm_control.ts`, and the legacy `--wrapper` option only accepts the canonical wrapper path.

After convergence, publication must activate the verified remote release and check `doctor`, `admin-metrics`, pending operations, task transitions, and timer/reconcile health. A pre-activation failure keeps the current release active and drained. A post-activation health failure permits one rollback attempt; a successful rollback is revalidated before drain exit, while a failed rollback keeps admission drained. Only after remote health succeeds may the publisher install and self-check the local client. Local installation takes an exclusive package lock, stages all eight client files and the sidecar, and runs `bun --no-macros <staged-package>/agent_vm.ts version` with a sanitized environment and a 30-second budget. Missing Bun or an unverified sidecar fails before active files change. Each file uses an exclusive temporary creation, fsync and atomic rename; the sidecar is installed last. A private format-2 recovery record binds every previous and target file's hash/mode, fixed destination and precise staging path before mutation. Clients refuse requests while this record exists, including when the sidecar is temporarily absent. The installer verifies the installed package before durably marking completion; recovery restores all previous files for an incomplete transaction or retains all verified target files for a completed transaction. It validates every destination, backup and staging entry before any recovery mutation and can itself resume after interruption. Unknown paths, unverified backups, partial/legacy recovery records and old Python-only installations require operator inspection and fail closed. Per-file atomic renames and the recovery fence provide a complete-package transaction; they do not claim a simultaneous directory exchange. A local client failure must preserve the old client, report a structured warning, avoid rolling back the healthy remote release, and keep drain closed. Manual rollback must verify the supplied previous bundle, roll back the remote transaction, install that same complete local client package, and exit drain only after both sides are healthy. Complete publication exits drain last.

The default publisher timeout is 300 seconds and the default poll interval is 1 second. Operators may lower those values but cannot exceed the timeout or poll safety bounds. Old releases are retained; deletion, automatic updates, resident brokers, and deployment inventory management are outside this contract.

## Public and private records

Public manifests, tests, and documents contain only relative source paths and neutral deployment placeholders. The live SSH alias, identity, credentials, release root, wrapper configuration, target paths, state database, timer inventory, and controlled staging observations remain operator-owned records outside this repository.
